# 项目版本变更规范

本规范用于 AI 判断是否需要修改版本号、怎么修改版本号，以及公共包消费者如何同步。若用户在当前任务中明确指定版本号，以用户指定为准，并在交付说明里解释原因。

## 版本归属

本仓使用现有前端 package 或小程序上传版本，不使用 Gradle group 或 Maven 发布。版本变化按实际构建入口和项目记录处理；后端公共库版本与契约由对应后端仓库独立维护，不把 Java 模板复制到前端。

## 什么时候改 version

- 修改生产代码、运行时配置、构建脚本、数据库脚本、公共示例，或会改变制品行为的依赖版本时，本批未提交改动只提升一次 `version`。
- 纯 README、AI 编程规范、注释说明、非运行时文档改动，不强制提升制品 `version`。
- 只修改 Nacos 远程配置且没有提交仓库文件时，不修改仓库构建版本，但交付说明必须写清 dataId、group、namespace 和验证结果。
- 同一批改动后续补测试、补文档、修格式，不重复提升版本。

## 怎么改 version

项目采用三段式 `MAJOR.MINOR.PATCH` 发布顺序，MINOR/PATCH 各为单个 0–9 数字，MAJOR 为无多余前导零的非负整数：

1. PATCH 小于 9 时只加 PATCH，例如 `1.2.8 -> 1.2.9`。
2. PATCH 为 9 且 MINOR 小于 9 时进位，例如 `1.2.9 -> 1.3.0`。
3. MINOR/PATCH 都为 9 时进位，例如 `1.9.9 -> 2.0.0`，不生成 `1.2.10` 或 `1.10.0`。
4. 修改前 fetch，核对远端 main/test/preprod、在途分支、tag 和已有制品占用；同一批未提交改动只升级一次，纯规范文档不升级业务制品，不创建空发布凑编号。
5. 历史错误编号只向前纠正，选择按三段整数比较高于所有已用版本的最小合法版本并记录映射，例如未被更高版本占用时 `1.3.105 -> 1.4.0`；不降级、不重写历史、不移动 tag、不覆盖同版制品。
6. 功能、兼容修复和破坏性改动均按此编号顺序；破坏性改动另行说明迁移、兼容影响和回滚，用户明确指定版本时记录其范围与占用核对。
7. 应用版本、依赖版本、接口和发现元数据版本分别管理，不批量替换所有数字；提交前写明原版本、新版本、进位依据和对应验证。

## 跨项目契约

- 前端升级接口、请求头或上传协议时核对后端精确版本和兼容范围；不复制后端工具源码或 RPC DTO。
- 前端依赖使用已存在的确定版本，不以未发布的后端候选假定环境已可用。
- 构建、测试、平台上传、发布和设备验收分别记录；纯规范变更不上传或发布业务包。

## 交付检查

- 最终说明写明旧版本、新版本、升级原因、是否发布 Maven、消费者是否同步、执行过哪些测试。
- docs-only 任务要明确说明未提升制品版本的原因。
